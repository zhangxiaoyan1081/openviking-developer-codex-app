## 问题与证据

用户反馈：连接和协作方式被略过、历史范围使用 HIL 单选、无整理进度卡、接续只交付 Markdown。

读取实际接入任务和 Codex 桌面日志后确认，2026-09-21 12:39:59 UTC、12:40:02 UTC 的接入任务启动 openviking-codex-app 失败，错误为 `MCP startup failed: No such file or directory (os error 2)`。本研发任务的 resources/list 也复现同一错误。插件在安装清单中 enabled=true，但任务中不存在可调用的卡片工具。技能和脚本可用不代表卡片 MCP 已启动。

旧安装配置使用 `command=node`、相对服务入口和插件缓存目录作为 cwd。错误本身不能区分解释器缺失与 cwd 被删除；二者都可能产生 ENOENT。此前的运行快照仅保护已经启动的服务，未保护启动前仍引用旧缓存的配置。原测试直接启动源码并继承终端 PATH，漏掉了这层安装环境。

此外，prepare_collaboration、publish_work、publish_report 原先只返回数据，依赖模型再调用 show 才显示；长期验证标记也可能让新的接入请求直接进入旧流程。这些分别是启动、展示契约和状态入口问题。

## 修复后的触发契约

| 触点 | 触发与展示 |
|---|---|
| 新接入、未提供 Key | show_onboarding(step="connection")，即使设备已验证也显示当前连接/更换 Key；不清除历史 |
| 继续已有接入 | show_onboarding(step="current")，恢复真实阶段 |
| 协作方式 | prepare_collaboration 直接携带 App 资源；新增规则采用后落盘再展示范围卡；已有同等授权可沿用，卡内可展开摘要 |
| 历史范围 | 新连接选择后已有规则可沿用时，显示范围选择；原生单选仅在真实不可用时兜底 |
| 导入清单 | review_import 直接显示；点击确认即切换整理卡，再由 Agent 执行导入 |
| 整理进度 | 当前卡按有限退避周期读取真实持久化回执；原文可用时先恢复摘要，不等抽取全部完成 |
| 接续 | publish_work 直接带卡片和完整状态，提供目标、进展、下一步、来源和继续按钮；脚本发布时必须补展示调用 |
| 报告 | publish_report 直接带工作台卡片；背景 get_state/import_status 不产生多余卡片 |

安装器为安装副本使用已核实的 Node/Python 绝对路径，并将入口/cwd 指向缓存以外的内容哈希快照。保留旧快照，避免升级打断已持有旧配置的任务。已有失效任务仍需要宿主重新加载配置，不能假定重新安装会热修复它。

## 验收分层

| 层次 | 自动检查 | 判定范围 |
|---|---|---|
| Python | 42 项：连接确认、规则合并、范围、导入、去重、回执、摘要等 | 后端行为 |
| stdio MCP | 4 项，包括最小 PATH、启动前删缓存、运行中删缓存、展示工具元数据与完整输出 | 安装启动和协议 |

| 集成流程 | 真实 MCP + Python + App SDK，模拟宿主消息桥；连接入口→规则采用→范围→跳过/导入→轮询→摘要→接续 | 组件之间的真实状态传递 |
| 已安装副本 | check:installed 从 codex mcp list 读取实际启动配置，使用最小 PATH 检查工具与 HTML | 本机安装副本可启动 |

| Codex 原生任务 | 尚未通过 | 当前电脑控制工具明确禁止操作 Codex 自身，无法自动完成原生对话的显示与点击验收；不能用以上结果代替 |

自动化使用临时私有状态和虚构资料，不修改用户 AGENTS.md、不切换 API Key、不上传测试历史。原有 UI 截图测试仍使用模拟数据；新增集成测试改为通过真实 MCP 调用驱动 Python 状态。

## 后续版本的发布检查

每次变更先跑 npm test，GitHub Actions 同样执行并保留模拟宿主截图。安装后跑 npm run check:installed 和 npm run check:codex-host。若存在宿主启动失败、没有真实 App 展示/点击证据，应标记原生验收未通过，不能交由用户重复走完整流程来发现基础故障。必要的宿主配置重载与产品验收分开说明。
